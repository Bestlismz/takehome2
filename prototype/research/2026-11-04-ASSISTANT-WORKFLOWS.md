# ลูกหลานทำงานให้ และบอกผลที่เกิดขึ้นจริง

วันที่ 4 พฤศจิกายน 2569 ตาม Asia/Bangkok

## จุดประสงค์

ลูกหลานเป็นผู้ช่วย AI ให้ครอบครัวดูแลคนที่เรารัก ผู้ใช้เล่าหรือขอทำรายการผ่านเสียงได้ในสายเดิม การใช้กล้องไม่ต้องสลับหน้าสนทนา แผงงานแสดงสถานะของเครื่องมือ ไม่แสดงข้อความสนทนาทั้งหมด

## โครงสร้างที่เลือก

เส้นทางเดิมคือ Realtime function call → ตรวจ schema จาก catalog → ตรวจ transcript ของรอบพูด → ตัวดำเนินการในแอป → browser outbox → HTTP workspace → PostgreSQL revision acknowledgement แล้วส่งผลกลับ Realtime

พิจารณาการเพิ่ม MCP สำหรับทุกการแก้ข้อมูล เทียบกับใช้ catalog และตัวดำเนินการที่ปุ่มกับเสียงใช้ร่วมกัน เลือกแบบหลัง เพราะไม่ต้องสร้างสิทธิ์เข้าถึงข้อมูลครอบครัวอีกชุด และสามารถตรวจเงื่อนไขยืนยันก่อนแก้ในจุดเดียวได้ การค้นเว็บไซต์สาธารณะใช้ backend OpenAI SDK ส่วน MCP และ RAG เดิมยังใช้สำหรับแหล่งความรู้ที่ตั้งค่าและอนุมัติแล้ว ไม่มี MCP สำหรับเข้าถึงประวัติผู้ป่วยภายนอกถูกเปิดใช้อัตโนมัติ

แผงงานอยู่ใน DOM ของหน้า/หน้าต่างเดิม จึงไม่เปิด dialog ซ้อนเพื่อแสดงความคืบหน้า และไม่ทำให้กล้องกับเสียงเริ่มใหม่ ในหน้าต่างฟอร์มแผงอยู่ต่อจากฟอร์มเพื่อไม่ทับช่องกรอก บนหน้าสนทนาแสดงเป็นแผงลอย ย่อได้และไม่แย่ง focus ใช้ role=status สำหรับข้อความความคืบหน้า ตาม [W3C status messages](https://www.w3.org/WAI/WCAG21/Understanding/status-messages)

## รูปแบบข้อมูล

- Tool activity มี id, label, status, message และ sources สถานะกำลังทำ รอยืนยัน สำเร็จ ผิดพลาด หรือยกเลิก เก็บในหน้าจอไม่เกินหกงาน ไม่ใช่ audit log ถาวร
- Proposal มี call, turn, session, createdAt ต้องตรงกับรายการที่เสนอ และยืนยันในรอบถัดไปของสายเดียวกันภายในห้านาที ถ้าเปลี่ยนค่าจะต้องอ่านทวนใหม่
- วันเวลาบันทึกใช้ ISO8601 ที่มี offset แปลงตาม Asia/Bangkok และปฏิเสธเวลาในอนาคตกับวันกำกวม
- ผล mutation มี storage.saved และ revision หลัง PostgreSQL ตอบรับ หากล้มเหลวไม่ส่งผลสำเร็จให้โมเดล ฉบับรอส่งยังอยู่ใน browser outbox

## เครื่องมือที่เพิ่มและแก้

รายการเสียงร่วม 58 คำสั่ง รวมเพิ่ม/แก้/ยกเลิกและอ่านนัด อ่าน/กรอง/แก้/ลบบันทึก ดูสรุป รับทราบ alert จัดการสายสาธิตและเสียง การอ่านรายการรองรับ limit/offset, วันที่ และคำค้น เพื่อเลือกบันทึกเก่าโดยไม่แต่ง id ส่วนกล้อง การสร้างข้อเสนอบันทึก และการค้นความรู้/เว็บมี Realtime functions เฉพาะ

record.delete ลบออกจากบันทึกปัจจุบัน สรุปที่เก็บไว้ก่อนหน้านี้คงหลักฐานเดิม จึงไม่ใช่การลบข้อมูลส่วนบุคคลออกจากทุกระบบ ไม่มีคำสั่งแก้แผนยาหรือขนาดยาแทนแพทย์

## หลักฐานตรวจสอบ

- JavaScript 65 และ Python 35 รายการผ่าน รวม 100 รายการ
- HTTP workflow ใช้เซิร์ฟเวอร์จริงกับ PostgreSQL luklaan_test ใน workspace สุ่ม แยกข้อมูลสองครอบครัว ทดสอบสร้าง/แก้ค่า/แก้เวลา/ลบบันทึก เพิ่ม/แก้/ยกเลิกนัด ความขัดแย้ง revision และสรุปหลักฐานเดิม ส่วนการเรียบเรียง AI ในกรณีนี้ใช้ stub เพื่อทดสอบการเก็บหลักฐานอย่างแน่นอน ล้างเฉพาะ fixture ของตน
- ทดสอบคำยืนยันคนละรายการ รอบเดียวกัน ข้ามสาย หมดอายุ คำปฏิเสธ และการยืนยันยกเลิกนัด
- ทดสอบว่าการตอบสำเร็จรอฐานข้อมูล และความผิดพลาดจากสายเก่าไม่ส่งเข้า Realtime สายใหม่
- บริการค้นเว็บจริงได้หลักฐาน WHO และ AHA ผลจาก browser ผ่านกำลังทำ → สำเร็จพร้อมลิงก์ และกรณีคำค้นไม่ผ่านแสดงผิดพลาดจริง
- OpenAI ยอมรับ schema Realtime ปัจจุบันซึ่งรวม 58 app actions และ 10 functions แล้ว ไม่แสดงหรือเก็บ ephemeral credential ในเอกสาร

## ขอบเขตของระบบจำลอง

ใช้ได้ในเครื่องเพื่อทดลองขั้นตอนที่เชื่อม API และฐานข้อมูลจริง ยังไม่ใช่บริการ production ที่รองรับข้อมูลผู้ป่วยจริงหลายครอบครัว Cookie workspace ไม่ใช่การพิสูจน์ตัวตนหรือการยืนยันความสัมพันธ์ผู้ดูแล ต้องมีบัญชี สมาชิกครอบครัว สิทธิ์ต่อบุคคล ความยินยอม และการตรวจการเข้าถึงก่อนเปิดบริการจริง

โทรศัพท์และการแบ่งปันผู้ดูแลยังเป็นสาธิต ไม่ได้ส่ง SMS โทรออก หรือแจ้งคนดูแลระยะไกล การกดรับทราบ alert ไม่เท่ากับมีบุคลากรรับดูแล เหตุฉุกเฉินไม่ใช่บริการเฝ้าระวังโดยแอป

ยังไม่ได้ประเมินบทสนทนาไทยด้วยการฟังจริงบนโทรศัพท์หลายรุ่น ความแม่นยำสำเนียง ภาพกล้องจริง และเสียงทีวีขณะสั่งลบ/แก้ข้อมูล ไม่อ้างว่าการแก้ prompt ทำให้ตัวเลขเหล่านี้ดีขึ้นแล้ว ข้อเสนอเสียงต้องผ่านการทดสอบกับผู้สูงอายุและคนดูแลก่อนใช้งานจริง

ตรวจหน้าจอรอบสุดท้ายที่ 1280 และ 390 พิกเซล ไม่พบ horizontal overflow แผงงานในฟอร์มไม่ทับช่องกรอก ปิดหน้าต่างย่อยแล้วแผงย้ายกลับหน้าหลักได้ แหล่ง AHA ขยายเปิดดูได้ ข้อความปฏิเสธคำค้นที่ไม่ผ่านแสดงเป็นความผิดพลาดก่อนค้นใหม่สำเร็จ Console error/warn ที่อ่านในรอบนี้ว่าง ภาพหลักฐานอยู่ในโฟลเดอร์ visualizations ของแชตนี้ ชื่อ luklaan-tool-activity-desktop.png และ luklaan-tool-activity-mobile.png

หลัก Model the Domain ทำให้ใช้ proposal ที่มีรอบพูดและสายสนทนา แทนการเชื่อค่า confirmed เพียงตัวเดียว สถานะสำเร็จของเครื่องมือต้องผ่าน durableToolResult และ PostgreSQL ก่อนส่งให้ Realtime
